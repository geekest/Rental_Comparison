# 修复导入表单标签、截图 OCR 映射与封面裁切

## 1. 任务目标

解决截图导入确认页在字段填入后无法辨认字段含义、OCR 内容识别后写入错误字段，以及整张平台截图直接覆盖房源卡片封面的问题。完成后，所有主要输入界面都使用始终可见的字段标签；截图 OCR 对用户提供的真实房源截图能更准确地识别名称、月租、面积、户型等字段；系统自动生成 16:9 房间封面并允许用户二次调整，同时保留原始截图作为房源证据。

## 2. 当前状态

- 截图导入入口位于 `Rental_Comparison/ListingImportView.swift`。
- `VisionListingRecognizer` 使用 Vision `VNRecognizeTextRequest` 获取纯文本；`ListingImportParser` 再基于整段文本做正则和行位置推断。
- 截图确认页、房源编辑页、详情内联编辑页以及多个辅助表单直接把 `TextField` 的标题当作占位文字；字段已有值时标题消失。
- 用户截图中 OCR 把状态栏时间写入房源名称，把租金截断为 `333`，并把整段标题/标签写入地址等错误字段。
- 已有 `Rental_ComparisonTests/ListingImportTests.swift` 覆盖少量整理后的文本 fixture，但尚未覆盖用户截图对应的原始 OCR 文本与字段错配。
- 当前工作区已有与本任务无关、尚未提交的 `Rental_Comparison/Info.plist` 显示名改动，以及 Xcode 用户状态目录；本任务不得混入或覆盖这些改动。

## 3. 目标状态

- 所有主要 `TextField` 都有持久字段标签，占位文字仅用于示例或空值提示。
- 截图确认页中至少明确显示房源名称、城市、月租、货币、地址、面积、户型的字段名。
- OCR 解析能过滤状态栏、导航和操作按钮等页面噪声；租金、面积、户型等结构化字段写入正确位置。
- 无法高置信度判断的字段保持为空，交给用户确认，不用错误文本填充。
- 旧数据模型和保存流程保持兼容。
- 截图导入后，房源卡片只使用 16:9 裁切封面，不展示平台截图中的标题、价格等下半部分。
- 导入确认页可调整封面的上下位置、左右位置和缩放，并重新生成封面。
- 原始截图继续保存在房源关联证据中，封面编辑不会覆盖或删除原图。

## 4. 范围边界

### 本次包括

- 原生 iOS App 的表单输入标签统一。
- Vision 本地 OCR 的识别配置、结果结构与房源字段解析。
- 用户提供截图对应的回归 fixture、单元测试和必要 UI 测试。
- 分阶段提交：问题 2 完成后先创建独立 commit；问题 1 修复再单独验证。
- 基于 OCR 文字位置自动推断房间图片区域，并生成固定 16:9 的本地封面图。
- 在截图导入确认页提供封面预览与二次裁切编辑。
- 使用现有 `.photo` 与 `.screenshot` 证据类型分别关联封面和原始截图。

### 本次不包括

- 云端 OCR、第三方付费 OCR 服务或远程生成式 AI。
- 针对所有房源平台和任意截图版式承诺 100% 准确。
- 修改数据模型、数据库迁移或新增生产依赖。
- 对所有房源平台截图保证自动裁切 100% 命中；识别失败时使用可编辑的默认裁切位置。
- 在已保存房源的详情页新增完整图片管理器；本次二次编辑入口位于导入确认流程。
- 将 `Rental_Comparison/Info.plist` 的既有显示名改动混入问题 2 的 commit。

## 8. 新发现与意外情况

- 发现：工程当前只有 OCR 后的纯文本，没有保留每段文字的坐标和置信度。
- 影响：页面状态栏、导航标签、标题和房源字段混在同一文本流中，解析器无法可靠判断来源位置。
- 处理方式：问题 1 阶段先用真实截图复现，再决定是否将 OCR 输出升级为带位置的结构化行。

- 发现：问题 2 的定向 UI 测试在 iPhone 16e Simulator 中被系统以 `signal kill` 终止，未进入业务断言。
- 影响：当前可确认编译和代码语义，但该次运行不能作为用户可见 UI 自动化通过证据。
- 处理方式：保留 UI 回归用例，记录环境失败，并在 Simulator 状态稳定后重跑；本阶段同时执行构建和 diff 检查。

- 发现：对用户原始截图直接运行 Vision 后，关键文字实际识别为 `¥3330/月`、`37.13m`、`3室2厅2卫` 和 `合租•龙湖时代天街-01卧`。
- 影响：本例的主因是后续解析与映射，不是 Vision 无法识别画面文字。
- 处理方式：用真实 OCR 文本建立回归测试，修正租金位数、标题分隔符、面积单位降级、完整户型和保守地址规则。

- 发现：同一份真实截图的 OCR 几何位置能稳定识别顶部 `VR / 视频 / 图片 / 评价` 与底部 `必看好房` 推荐条。
- 影响：无需平台专用模板即可把两组文字之间的房间画面作为首选裁切区域。
- 处理方式：优先按几何标记居中裁切，缺少标记时回退到可编辑的默认位置；真实截图生成结果只包含房间主体。

- 发现：环境未提供 `ios-debugger-agent` 要求的 XcodeBuildMCP UI 交互工具。
- 影响：可以完成 Simulator 构建、安装、启动和截图，但不能可靠自动操作系统照片选择器并遍历封面编辑界面。
- 处理方式：使用 `xcodebuild`、`simctl`、生产 OCR/裁切代码和通用单元测试完成验证，并把系统选择器端到端点击列为未验证。

## 9. 决策记录

### Decision：字段名使用持久标签

选择：使用 `LabeledContent` 语义的统一组件，左侧显示固定字段名，右侧显示输入值或示例占位文字。

原因：字段有值后仍可理解，符合 iOS 表单和辅助功能语义，也满足用户要求的“价格：XXX”结构。

备选方案：在每个输入框上方增加独立 caption；信息明确但页面会明显变长，且不符合当前紧凑 Form 版式。

影响：输入区域布局会从纯文本行变为固定标签与输入内容的双列结构。

### Decision：OCR 字段解析采用行级上下文并保持保守

选择：保留 Vision 原生阅读顺序，解析器按行识别租赁标题、标签后数值和明确地址；无法证明是地址的文本保持为空。

原因：用户截图的 OCR 文本本身正确，错误来自整段文本正则截断和误判。行级上下文能用较小改动修复本例，并避免将标题继续写入地址。

备选方案：将坐标、置信度和平台版式全部引入结构化解析；准确性上限更高，但需要更大接口调整和更多多平台 fixture。

影响：截图识别对常见中文房源截图更可靠，但仍不承诺任意平台、低清晰度截图 100% 正确。

### Decision：原始截图与封面使用现有证据类型双轨保存

选择：自动裁切生成的封面保存为 `.photo` 证据，原始导入截图保存为 `.screenshot` 证据；房源卡片优先投影 `.photo`，没有封面时回退旧 `.screenshot`。

原因：既能让卡片只消费封面，也能在房源证据中完整保留原图，并且不新增持久化字段或迁移。

备选方案：给 `Evidence` 或 `Listing` 增加专门的原图和裁切参数字段；语义更直接，但会扩大数据模型、兼容和迁移风险。

影响：导入草稿增加短生命周期字段，旧工作区继续可解码；自动裁切结果是独立媒体，重新编辑不会破坏原图。

## 11. 风险与回滚

- 双列标签可能在大字号或长标签下压缩输入区域；需要检查动态字体与多行字段。
- OCR 规则过于依赖单个平台版式会伤害其他截图；解析必须保守并保留已有 fixture。
- Vision 对低清晰度、压缩、复杂背景文字的识别有上限，无法承诺所有截图 100% 准确。
- 问题 2 可通过独立 commit 回滚；问题 1 将保持独立改动和测试。
