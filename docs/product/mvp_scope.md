# Rental Comparison MVP 范围

## 文档状态

- 状态：已确认
- 最近更新：2026-08-19
- 依据：[产品简述](product_brief.md)
- 当前交付：Web MVP 已冻结为历史验证版本；原生 iOS 的 v2 P0 范围以 [Decision Readiness 重构规格](../specs/spec_002_decision_readiness_rebuild.md) 为准

## v2 P0 目标

验证已有多个候选的租房者，能否通过 Facts、Evidence、Unknown 与 VerificationTask 更快建立足以知情决策的证据，而非维护一份完整租房字段表。

本轮包括：低摩擦 Quick Capture、v1 → v2 本地迁移、事实来源与确认状态、Difference-first Compare、高影响 Unknown、VerificationTask、Decision Readiness、可解释最终确认，以及 Universal Core 与 China Regional Template。

本轮不包括：房源搜索、供给聚合、账户、云同步、支付、综合评分、自动赢家、远程 AI、Share Extension、URL Provider Adapter、地图自动通勤、多人协作、Android 或 iPad 专门布局。

## 历史 Web MVP 目标

验证中国大陆城市长租用户是否愿意录入多个真实租赁方案，并通过统一的成本、通勤、条件和看房证据完成一次可说明的候选判断变化。

MVP 不以自动提取准确率、视觉完整度或最终签约率为主要目标。它首先验证“独立的租房决策工具是否成立”。

## 本次包括

### P0-1：选房任务

- 用户可以创建一次选房任务，记录城市、地区模板、默认货币、面积单位、预计居住月数、基础条件和主要通勤目的地。
- 同时只支持一个进行中的任务。
- 完成的任务保存在当前设备，并允许重新打开。

### P0-2：租赁方案录入

- 首次保存只要求自定义名称、城市、整租或合租、月租和货币。
- 地址、来源、面积、户型、租约、费用、通勤和看房信息均允许未知并后补。
- 支持绑定本地截图，并使用本地 OCR 将可稳定识别的字段匹配为待确认建议。
- OCR 结果经用户确认后才参与比较和计算。
- 支持浏览器定位、地图搜索与选点确认房屋位置；定位或地图不可用时允许手动填写地址。
- 位置能力仅在用户打开补充信息后调用浏览器定位或 OpenStreetMap 服务；不使用时不上传地址或坐标。

### P0-3：费用与现金压力

- 费用以结构化明细记录，包含名称、金额、货币、一次性或周期性、付款周期、是否可退和是否已确认。
- 展示首期现金压力和月均居住成本，并展开计算公式。
- 未知费用不按 `0` 计算；计算结果必须提示尚未填写的费用。

### P0-4：条件与偏好

- 条件的重要程度包括硬性条件、普通偏好和不关注。
- 单套方案对条件的结果包括符合、不符合和未知。
- 首版内置月均预算上限、最晚入住日期、整租或合租、最大通勤时间及自定义条件。
- 中国大陆模板提供宠物、电梯、停车、做饭等常见条件，但不强迫用户填写。

### P0-5：候选池与横向比较

- 录入 2 套方案即可比较，最多同时选择 5 套。
- 手机屏幕重点展示 2～3 套，其余通过横向滑动查看。
- 用户可以指定一套基准房源固定在最左侧；基准只用于比较，不代表推荐。
- 比较突出硬性冲突、差异和未知项，不生成综合分数或赢家。
- 整租和合租只比较个人实际支出、首期现金、通勤、条件及风险等同口径信息。

### P0-6：看房记录

- 使用结构化看房清单。
- 每个检查项具有未检查、无问题和有问题三种结果。
- 只有有问题时才可以补充文字和少量本地照片，且两者均非必填。
- 中国大陆模板包括采光通风、噪音、潮湿发霉、水压排水、家电设施、安全门禁、网络信号、周边环境及图片与实物差异。
- 用户可以隐藏模板项目或增加自定义项目。

### P0-7：决策状态

- 租赁方案状态只包括候选和已淘汰；已淘汰方案可以恢复为候选。
- 重点考虑是可同时应用于多套方案的标记，不属于状态。
- 每次选房任务只能确认一套最终房源。
- 最终房源可以撤回到候选池重新比较；撤回后选房任务重新变为进行中。
- 用户可以重新确认原房源或选择另一套最终房源，并保留本地变化记录。

### P0-8：决策结果与反馈

- 最终结果页展示最终房源、关键成本、硬性条件冲突、看房异常、未确认事项、淘汰方案及最终选择理由。
- 用户可以导出不包含原始截图和看房照片的决策报告。
- 反馈只包含用户主动填写的文字、问题类型和随机测试编号，不自动附带房源内容或页面数据。
- 用户主动选择提交截图时，必须再次确认。

### P0-9：本地测试摘要

- 原型在设备本地生成测试完成摘要。
- 摘要只包含方案数量、是否比较、是否记录看房问题、是否调整重点考虑或淘汰、是否确认最终房源。
- 摘要不包含地址、租金、备注、截图或照片。
- 只有用户主动提交时，摘要才会发送给开发者。

## 中国大陆地区模板

### 基础信息

- 自定义名称、城市、整租或合租、地址、来源链接或本地截图。

### 空间信息

- 整套面积或私人空间面积、面积单位、户型、楼层、电梯。

### 租约信息

- 可入住日期、租期、预计居住月数、付款周期。

### 费用信息

- 月租、押金及其他自定义费用；货币允许用户自由填写。押金默认可退，其他费用以名称、金额和每日/每月/每季度/每半年/每年/一次性周期记录。

### 居住条件

- 家具家电、做饭、宠物、停车及自定义条件。

除首次保存需要的 5 个字段外，其他字段均允许未知。

## 本次不包括

- 账户注册、登录、业务服务器和云同步；
- 多人协作、免安装评分或共享候选池；
- 任意房源平台链接自动解析；
- 远程生成式 AI 识别；
- 地图路线与通勤时间自动计算；
- 语音记录、语音转写和复杂弱网同步；
- 综合评分、权重模型和自动推荐；
- 支付、订阅和购买恢复；
- 租后 App 移交；
- 香港、台湾及其他地区模板；
- Android、iPad、正式 Web 产品和 App Store 发布。

## 核心用户故事

- 作为正在比较多套房源的租房者，我希望快速保存一套不完整的候选方案，以便先建立候选池再逐步补充资料。
- 作为关心真实支出的租房者，我希望区分首期现金压力和月均居住成本，以免把押金和实际费用混为一谈。
- 作为会比较整租和合租的租房者，我希望只比较同口径信息，以免面积或总价造成误导。
- 作为有明确底线的租房者，我希望看到硬性条件冲突和未知项，以便优先排除不可接受的方案。
- 作为即将实地看房的租房者，我希望快速记录异常和照片，以便之后不会混淆不同房源。
- 作为最终决策者，我希望标记多套重点考虑方案并确认唯一最终房源，以便完成本次选房任务。
- 作为可能改变决定的租房者，我希望撤回最终房源并重新比较，以便新信息出现时不会被不可逆状态锁住。

## 验收标准

- 用户可以在只填写 5 个必填字段的情况下保存第一套租赁方案。
- 用户可以选择 2～5 套候选方案进入比较。
- 比较页面不会把未知费用显示为 `0`，也不会生成综合赢家。
- 费用公式能区分可退押金和不可退费用。
- 整租面积和私人空间面积不会被当作同一指标自动比较。
- 用户可以将已淘汰方案恢复为候选。
- 用户可以标记多套重点考虑方案。
- 用户只能确认一套最终房源，并可以将其撤回到候选池。
- 房源内容在正常使用过程中不上传到产品业务服务器。
- 用户可以导出最终决策报告。

更完整的流程、异常与数据规则见 [核心流程规格](../specs/spec_001_core_flow.md)。

## 验证计划

### 样本

- 至少 10 名有效完成者；
- 首轮计划招募 3～4 名陪同测试用户和 8～12 名自行使用用户；
- 用户必须拥有至少 2 套真实候选，并预计在 14 天内继续比较或看房。

### 通过门槛

- 至少 60% 录入 3 套真实方案；
- 至少 50% 完成比较并产生可说明的候选判断变化；
- 首套方案录入中位时间不超过 3 分钟；
- 实际看房用户中，至少 40% 回来补充证据。

### 暂停或转向条件

出现下列任意两项时，暂停进入原生 App：

- 少于 40% 的用户愿意添加第 2 套方案；
- 多数用户认为维护数据比共享表格更麻烦；
- 用户无法指出任何由产品促成的决策变化；
- 看房后几乎无人重新打开产品；
- 整租与合租持续造成比较口径误解；
- 即使有人引导，核心数据仍无法在合理时间内录入。
